## The mental model

Human intent may begin in a support system, issue tracker or direct conversation. The provider
remains the human workflow authority. Once the Fleet accepts the outcome, it needs a durable
identity that does not disappear with the incoming notification or first worker.

```text
external intent → acceptance → stable Task identity → active owner
```

Acceptance is a meaningful boundary. Not every event deserves a Task, and an Agent should not turn
every alert into work. Reconciliation checks existing intent, duplication, scope and authority
before the organization commits.

## Worked example: accept the checkout outcome

The support event says:

> Customer 481 could submit an address whose validity period ended yesterday.

The provider event remains evidence. First Mate reconciles it with the current project and finds no
existing Task. The company accepts:

> Checkout rejects expired addresses server-side and the fix is delivered through the payments
> repository’s reviewed workflow.

That outcome is stable even if diagnosis later shows the bug is in a shared date library rather
than checkout. The execution strategy can change without rewriting what the company accepted.

The Task does not claim the support event is true in every detail. It preserves the outcome the
organization agreed to carry.

## What changes at this layer?

- External signals are reconciled instead of automatically becoming work.
- Accepted intent survives notification loss and worker turnover.
- People can ask whether the organization has accepted an outcome.
- Execution still needs one accountable active owner.
