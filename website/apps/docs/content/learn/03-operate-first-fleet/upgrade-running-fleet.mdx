## The mental model

A running Fleet has several version states:

```text
writable AgentOS checkout
loaded harness instructions
database migration journal
running image digest
```

Changing one does not magically change the others. A Git checkout can be current while Pi still
uses older loaded instructions. A new Skill can be loaded while old runtime TypeScript remains in
the image.

## Worked example: adopt a newer release

First Mate discovers a newer stable AgentOS release while fetching remotes read-only. It reports
the available revision without changing its dirty checkout or restarting itself.

With approval, the upgrade procedure:

1. verifies the immutable release and manifest;
2. reads intervening changes and migrations;
3. inspects the server-side diff;
4. preserves the current PVC and recovery boundary;
5. applies ordered forward migrations;
6. rolls the image one Mate at a time by digest;
7. verifies the same home, native session, database identity and loaded instructions.

A Markdown-only preview can update the reviewed checkout and invoke a safe harness reload. An
executable change needs the exact image. Neither path uses `kubectl cp`, a mutable tag or
uncommitted source.

## What changes at this layer?

- The Fleet can improve without discarding identity or work.
- Loaded behavior is treated as runtime state.
- Stable and preview revisions have explicit provenance.
- Upgrade remains a consequential, observable reconciliation.
